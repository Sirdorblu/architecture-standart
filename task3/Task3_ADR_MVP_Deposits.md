# ADR: MVP онлайн‑открытие депозитов в банке «Стандарт»

**Статус:** proposed  
**Версия:** 1.0  
**Дата:** 2025-10-23  
**Автор:** Команда архитектуры / инициатор: менеджер цифровой трансформации

---

## Название задачи
Онлайн‑открытие депозитов: MVP для сайта и интернет‑банка.

## Функциональные требования (Use Cases)

| № | Действующие лица или системы | Use Case | Описание |
|:-:|:-|:-|:-|
| UC1 | Клиент, Сайт, Система кол‑центра | Заявка с сайта новым клиентом | Клиент выбирает депозит и отправляет ФИО+телефон на сайте и лид создаётся в системе КЦ и оператор звонит, уточняет условия, при необходимости формирует предварительные условия в АБС и назначает визит для идентификации. |
| UC2 | Клиент, Интернет‑банк, Сервис заявок, АБС | Подача заявки в ИБ существующим клиентом | Клиент аутентифицирован в ИБ, видит персональные ставки и выбирает счёт/сумму и отправляет заявку и подтверждает СМС‑код и заявка попадает в Сервис заявок и БО подтверждает ставку в АБС и результат возвращается в ИБ. |
| UC3 | Бэк‑офис депозитов, АБС (модуль ставок), Сервис заявок | Обработка и подтверждение ставки | Менеджер БО работает в АБС: рассчитывает/подтверждает ставку (в т.ч. импорт из XLS на переходный период) и АБС меняет статус заявки и Сервис заявок синхронизирует статус. |
| UC4 | Клиент, СМС‑шлюз, АБС/Сервис уведомлений | Уведомления | После подтверждения ставки и открытия депозита клиент получает СМС, в ИБ обновляется статус. |
| UC5 | БО депозиты, БО кредиты, АБС | Ведение ставок | Совместное ведение справочника ставок: роли и раздельный доступ, импорт/экспорт XLS до миграции на полноценный справочник. |

## Нефункциональные требования

| № | Требование |
|:-:|:-|
| NFR1 | Транспортная защита: HTTPS, TLS ≥1.2/1.3 |
| NFR2 | Доступность ИБ и онлайновых сервисов ≥99.9% 24 на 7 |
| NFR3 | Горизонтальное масштабирование фронтов, балансировка по серверам/ЦОД. |
| NFR4 | Производительность: p95 API ≤300мс, p99 ≤500мс, доставка СМС ≤30с. |
| NFR5 | Наблюдаемость: трассировка, метрики SLI/SLO, аудит действий. |
| NFR6 | Технологический ре‑юз: .NET Framework 4.5 (ИБ), Java/Spring (новые сервисы), MS SQL и Oracle, очереди - Kafka как целевая шина. |
| NFR7 | Идемпотентность и надёжность интеграций: ретраи, Outbox/Inbox. |
| NFR8 | Защита аутентификации: СМС‑OTP — допустимо для MVP, план миграции на более стойкие факторы. |

## Решение

### Архитектурная идея
Для надёжности обмена REST + Outbox/Inbox и очереди (Kafka в целевой модели). СМС‑уведомления — через существующий СМС‑шлюз.

### Основные компоненты
1. **Интернет‑банк (ASP.NET MVC 4.5, MS SQL)** — UI/монолит, модуль «Депозиты‑MVP», подписки/пулы кэширования ставок.  
2. **Сервис заявок на депозиты (Spring Boot, MS SQL)** — API заявок, статусы, Outbox, интеграция с АБС и СМС‑шлюзом.  
3. **АБС (Oracle, PL/SQL, клиент Delphi)** — учёт, модуль ставок, изменение статусов заявок.  
4. **Система кол‑центра (React + Spring Boot, PostgreSQL)** — приём лидов с сайта, работа операторов.  
5. **Сайт (PHP + React.js)** — публичные ставки, форма лида.  
6. **СМС‑шлюз ↔ Телеком‑оператор** — уведомления и OTP.  
7. **Шина сообщений (Kafka, по мере готовности)** — событийные интеграции, ретраи, партиционирование.  

### Ключевые интеграции
- Сайт и Система КЦ: REST (создание лида).  
- ИБ и Сервис заявок: REST + JWT, TLS, подтверждение заявки через СМС‑OTP.  
- Сервис заявок и АБС: сервисный адаптер/шлюз (REST/SOAP/DB‑процедуры по контракту), идемпотентные операции.  
- АБС и СМС‑шлюз и Клиент: уведомления, статусы возвращаются в Сервис заявок.  

### Выбор технологий
- **TLS 1.2+/HSTS** — защита канала.  
- **СМС‑OTP** — компромисс в MVP с планом на TOTP/пуш‑подтверждение.  
- **Kafka** — целевая очередь, до миграции ИБ — Outbox + периодический публикатор.  

## Альтернативы
2. **Сервис ставок как отдельный микросервис** — гибко, но увеличивает число интеграций в MVP, перенесено на следующий этап.  
3. **Единая БД для заявок в Oracle** — упрощает транзакции с АБС, но усложняет доступ .NET/Java‑командам и снижает независимость релизов.

## Недостатки, ограничения, риски
- Задержки из‑за ручной обработки БО до финального этапа.  
- Вертикальная масштабируемость АБС остаётся системным ограничением, требуется троттлинг/буферы.
